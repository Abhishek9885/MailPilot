# Phase 13.3 — Threat-model security audit

**Audit date:** 2026-11-22  
**Scope:** source review and regression testing of the local MailPilot workspace. This was not an independent penetration test, production-cloud review, or legal/privacy assessment.

**Dependency verification update:** 2026-11-25. The patched dependency versions and current npm advisory results are recorded below; hosted configuration was not audited.

## Threat model and findings

The audit treated a malicious sender as able to control message text, headers, MIME parts, links, filenames, and quoted content; a signed-in user as able to alter request parameters and replay requests; and provider/network failures as potentially large, slow, duplicated, or uncertain. The main assets are mailbox content and derived records, OAuth credentials, user identity, persisted workflow state, and approved external actions.

| Priority | Finding | Impact | Status and regression coverage |
|---|---|---|---|
| P1 / High | Gmail and Calendar OAuth callback transactions were signed and owner-tagged but did not require the initiating live session. A callback could finish after the browser session changed. | A consent flow could attach an external mailbox/calendar grant to the wrong active account. | Fixed by including the initiating session ID in the short-lived transaction and verifying the current, unexpired, active session belongs to that exact user/session before exchanging the code. Gmail and Calendar cross-session callback tests assert no provider exchange or persistence occurs. |
| P1 / High | Production could use the known Calendar token-encryption placeholder when event writes were disabled, even though Calendar OAuth could still store credentials. | Calendar refresh tokens could be encrypted with a publicly known development value. | Fixed: production now requires an exact base64-encoded 32-byte Calendar key regardless of the event-write flag. Environment regression tests cover placeholder rejection and valid key acceptance. |
| P1 / High | Pino's service-signature redaction path used an invalid unquoted hyphenated header path. | Importing the API logger could throw during service startup; the internal service signature was not covered by a working redaction rule. | Fixed with a quoted bracket path. A logger regression test verifies the signature value is censored. |
| P1 / High | API routes had no shared request limiter. | Repeated OAuth, AI, sync, or action requests could consume provider quota or service capacity. | Fixed with Redis-backed IP and session budgets, hashed keys, bounded Redis timeouts, `Retry-After`, and fail-closed behavior when Redis is unavailable. Tests cover route limits, health exemptions, key privacy, and store failure. |
| P2 / Moderate | Gmail success responses were parsed with `response.json()` before MIME limits could apply; error responses were also fully read to inspect quota markers. | An unexpectedly large provider response could consume excessive API memory before message parsing limits. | Fixed by streaming responses through an 8 MiB JSON cap and 64 KiB error-body cap. Regression tests cover oversized success and error responses. |
| P2 / Moderate; resolved before release | Next.js 16.4.1 was within the affected range of the November 2026 security release. The vulnerable upstream cache behavior requires Cache Components and specific `use cache`/`unstable_cache` patterns; no such pattern was found in `apps/web/src` during this audit. | Exposure depended on enabled framework features and deployment shape. | Updated `next` and `eslint-config-next` to 16.4.6, updated the Effect transitive dependency to patched 3.22.2, and refreshed compatible ESLint tooling. `npm audit` and `npm audit --omit=dev` report zero vulnerabilities. The patched production build and local tests pass; PostgreSQL and live-provider checks remain pending. See the [official Next.js security release](https://nextjs.org/blog/november-2026-security-release). |

## Controls reviewed

| Threat area | Observed control and evidence | Remaining exposure |
|---|---|---|
| Prompt injection | Email and retrieved text are marked untrusted in analysis, drafting, RAG, and planning. The AI tool registry is read-only and allowlisted; model output is schema-validated. Synthetic adversarial cases exist in the RAG and offline evaluation fixtures. | Prompt wording cannot guarantee correct model behavior. Keep email content out of policy/system messages; treat every model result as untrusted. Evaluation fixtures are small and do not prove resistance to novel attacks. |
| Cross-user access | Express derives identity from the validated session; data stores use owner predicates and compound owner foreign keys. RAG tools inject trusted identity outside model arguments and verify source ownership. Route, store, and database tests cover owner mismatches. | PostgreSQL integration tests and persistent checkpointer restart tests were not run in this audit environment because Docker is unavailable. Run them against an isolated throwaway test database before release. |
| Authentication and OAuth | Session revocation/expiry and CSRF checks are present. Gmail and Calendar callbacks now bind to the same live initiating session and validate identity/scope response fields before storing a grant. Redirect destinations are normalized/allowlisted. | Google consent-screen configuration, scope verification, external callback behavior, and production cookie/proxy configuration need deployment verification. |
| OAuth token storage | Gmail/Calendar refresh tokens remain in Express-owned storage and use AES-256-GCM encryption; FastAPI does not receive Gmail tokens. Production key shape is validated. | The current encryption master key is environment-managed rather than KMS envelope-encrypted. Key rotation, backup recovery, and secret-manager access controls are operational launch work. |
| MIME, HTML, and attachments | Parser limits MIME nesting, part count, header bytes, decoded body size, and provider response size. HTML is sanitized; no `dangerouslySetInnerHTML`, automatic remote-image load, attachment fetch, or email-controlled URL fetch path was found. Parser tests cover malformed/unsafe HTML and limits. | Sanitized hyperlinks can still lead a user to a phishing site when clicked. Attachment contents are not parsed. Keep link-opening behavior user initiated and external egress restricted. |
| Tool arguments and network fetch | FastAPI uses strict typed arguments, a fixed read-only tool allowlist, trusted identity injection, per-tool timeouts, bounded retries, and safe structured errors. Provider URLs are service configuration; email content does not select a fetch URL. | Infrastructure egress policy and DNS controls were not inspected. Restrict outbound traffic to approved provider/service endpoints and prevent public users from changing provider URLs. |
| Approval bypass, replay, duplicates | Proposals bind owner, immutable payload hash, expiry, source evidence, and idempotency key. Approval/execution uses persisted state transitions and atomic claims; Calendar writes revalidate immediately before provider execution. Gmail send is not implemented; Calendar event writes are disabled by default. Tests cover changed payload, owner mismatch, expiry, replay, duplicate, concurrency, timeout, and reconciliation paths. | Calendar conflict preflight cannot eliminate races with other calendar clients. Do not enable provider writes until OAuth scopes, deployment configuration, security tests, and release approval are verified. |
| Sensitive logging | Request logs omit query strings and bodies. API and AI logs use safe error classes/metadata; provider prompts, email content, tokens, and response bodies are not logged. The invalid Pino header rule is fixed and has a regression test. | The logger test validates configured redaction for a representative secret, not every future log call. Review new fields and trace sinks before adding them. |
| Rate limits and abuse | Shared Redis counters apply a global IP limit of 300 requests per 5 minutes and narrower budgets: OAuth 20/10 minutes, AI generation 10/minute, Gmail sync 3/10 minutes, and proposal/action routes 12/minute. Redis failure returns a retryable 503 for limited requests. | Limits are starting values, not load-tested capacity targets or provider spend caps. `TRUST_PROXY_HOPS` must match the trusted ingress chain; the edge must overwrite forwarded headers. Redis outage blocks requests covered by the limiter. |

## Residual risks and release conditions

- No independent penetration test, deployed-cloud IAM/network review, third-party secret scan, or Google OAuth verification was performed here. Local npm advisory checks passed with zero findings.
- Docker Desktop/PostgreSQL was unavailable. Database migration/reset tests, database-backed owner constraints, vector queries, and PostgreSQL checkpointer recovery remain unverified in this run.
- The available tests exercise API routes/services, AI workflows, and mocked providers; no full browser-to-PostgreSQL-to-Google end-to-end run was possible. Redis limiter behavior was tested through its store interface, not against a live Redis server.
- OAuth token encryption uses an application-held master key. Before production, move it to managed secret/KMS handling, rehearse rotation and restore, and confirm backups are protected.
- The request limiter reduces request abuse but does not impose a provider spend ceiling. Set provider usage alerts and an explicit cost budget before enabling real mailbox-scale AI use.
- The AI evaluation set and classifier test set are small synthetic fixtures; passing them is regression evidence only, not a product-quality claim.
- Next.js and `eslint-config-next` are now pinned to 16.4.6; npm reported zero vulnerabilities across development and production dependencies after the update. The source review found no Cache Components or `use cache`/`unstable_cache` use, but the hosted deployment still needs its own configuration and verification.
- Review allowed outbound egress, trusted proxy configuration, log retention/access, OAuth scope approval, and deletion behavior in the deployed environment.
